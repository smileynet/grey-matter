# CI staging and registry attempt evidence

Research date: 2026-10-23. This records implementation constraints for ticket 68.
The manual CI publisher and durable registry attempt barrier remain unfinished.
Consumed by [ADR-0002](../decisions/0002-reviewed-ci-staging.md).
No release, tag, registry upload or stable promotion ran during this research.

## Staging and later review

[L2:verified] GitHub manual dispatch resolves a branch or tag and requires a workflow
registered on the default branch. Verify the observed run head and checkout against
the expected candidate commit C. A reusable workflow reference cannot interpolate
an input SHA; pass the later review commit R as data to a pinned workflow.
Sources: [dispatch event](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch),
[dispatch API](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event),
[reusable workflows](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows).

[L2:verified] Actions artifacts expose IDs, digests, expiration and run identity.
Preserve run attempt and per-file hashes as well: a run ID alone cannot identify
bytes across reruns. Explicitly configure download-artifact v8's
`digest-mismatch: error`; the general tutorial's warning-only description conflicts
with the action contract. Artifacts, logs and associated run evidence have finite
retention and cannot serve as permanent upload-attempt records.
Sources: [artifact API](https://docs.github.com/en/rest/actions/artifacts#get-an-artifact),
[download action](https://github.com/actions/download-artifact),
[tutorial](https://docs.github.com/en/actions/tutorials/store-and-share-data#validating-artifacts),
[retention](https://docs.github.com/en/organizations/managing-organization-settings/configuring-the-retention-period-for-github-actions-artifacts-and-logs-in-your-organization).

[L1:verified] A disposable cargo-dist 0.32.0 generation probe confirms that
`create-release=false` plus a custom publish hook still uploads assets and undrafts
the release in `host`, before the custom hook. The workflow generated by the probe had
SHA-256 `1ae7ec2d21bc1a74238b1c41cc4e385a7300283fd07af3cb80da7addd2a3559b`.
This closes the generation-probe gap in [hook research](dist-publisher-hooks.md);
it does not verify a replacement workflow. A checked generator wrapper must remove
all earlier publication paths before a custom publisher can become authoritative.

## Durable attempt barrier

[L4:verified] Cargo publish packages source before uploading; its documented CLI
does not accept an existing sealed crate. Index polling can time out after a
successful upload. The registry index checksum identifies the uploaded crate bytes.
Sources: [Cargo publish](https://doc.rust-lang.org/cargo/commands/cargo-publish.html),
[Cargo package](https://doc.rust-lang.org/cargo/commands/cargo-package.html),
[registry index](https://doc.rust-lang.org/cargo/reference/registry-index.html).

[L4:verified] Immutable GitHub releases lock assets and tags, while title and notes
remain editable. Draft assets can be deleted or renamed; incomplete uploads can
leave `starter` assets. A receipt stored there survives runner loss but is mutable
until publication. Authenticate and paginate draft discovery, bind release/asset
IDs, and refuse replacement or differing bytes.
Sources: [immutability](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases),
[release API](https://docs.github.com/en/rest/releases/releases),
[asset API](https://docs.github.com/en/rest/releases/assets).

Proposed design, not implemented: generate deterministic receipt bytes containing
product, version, candidate commit C, registry and crate hash, plus
`uploadMayHaveBeenAttempted:true`. Include those bytes in the review.
Observe registry and any existing receipt before staging. Upload ordinary draft
assets first; create the receipt immediately before a permitted Cargo attempt.
Only this execution's successful receipt creation grants initial attempt permission.
A timeout followed by matching receipt readback consumes that permission rather
than proving exclusive ownership. A preexisting receipt plus missing registry
state requires explicit retry authorization. If the registry contains a non-yanked version whose checksum matches the sealed
crate, skip Cargo and permit GitHub recovery. Receipt deletion requires externally retained
IDs or an explicit no-out-of-band-deletion assumption.

The shared reconciler now supports fixture-tested `publish:false` draft staging.
This boundary alone supplies neither the receipt barrier nor a live CI publisher.
A dry-run package comparison and post-upload checksum also do not prove that Cargo
will upload only the sealed bytes. Pin the toolchain and source/config, then verify
the actual transport against a harmless mock registry before claiming that stronger
contract. No custom raw registry uploader is proposed.

## Remaining evidence

Implement and check the generator wrapper, build-only staging, artifact download
provenance, pinned Cargo transport probe, durable receipt ownership and CI dispatch
recovery. Observe effective retention and rerun artifact behavior in a harmless
staging run. Keep approved-version candidate validation separate from source-smoke
fixtures and earlier hosted platform runs.
