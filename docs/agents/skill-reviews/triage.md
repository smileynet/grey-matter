# triage

- Bucket: engineering. Invocation: model-invoked since 2026-10-22 (was user-invoked; orchestrators like wrap-session must call it via the Skill tool, which Claude Code refuses for user-invoked skills; enforced by check-invocation-policy.mjs Check 3).
- Verdict: **adapt**: keep the state machine and both reference files; recast around the
  PR-as-external-surface / tkt-as-internal-unit **adapter**; put evidence teeth on
  verification; make `.out-of-scope/` matching surface-and-confirm.

## What it is

A maintainer-driven state machine for triaging work. Two category roles (`bug`,
`enhancement`), five state roles (`needs-triage`, `needs-info`, `ready-for-agent`,
`ready-for-human`, `wontfix`). Multi-file: SKILL.md + **AGENT-BRIEF.md** (durable,
behavioral, acceptance-criteria specs) + **OUT-OF-SCOPE.md** (a `.out-of-scope/` KB of
rejected enhancement concepts for institutional memory + dedup). Per item: gather context
(redundancy search + `.out-of-scope/` check), recommend category+state, **verify the
claim** (reproduce a bug / run a PR's tests), grill if underspecified, apply outcome.
Every AI-posted comment carries a "generated by AI during triage" disclaimer.

## What it does for the user

Turns a noisy inbox of requests into a small, legible set of states, and pre-qualifies
accepted work into agent-ready briefs so an AFK agent can pick it up. The verify gate
stops unconfirmed claims from becoming "ready".

## Prior art (agent-filtered)

Research confirmed a tight recombination of established practice:

- **State-machine labels** = standard triage lifecycle (Kubernetes `triage/*`, Rust
  `S-*`, GitHub defaults `bug`/`enhancement`/`wontfix`).
- **`ready-for-agent`** = descendant of `good first issue` / `help wanted`, taken to its
  logical conclusion (pre-specified so low-context contributors can start).
- **Verify-the-claim** = textbook bug-repro gate (confirmed vs unconfirmed).
- **Agent brief** = Definition of Ready + acceptance criteria + scope fencing; a
  path-free behavioral spec is what spec-driven development converges on.
- **`.out-of-scope/`** = a lightweight ADR / declined-feature log (one file per concept,
  mirroring one-ADR-per-decision).
- **AI disclaimer** = emerging provenance / `[bot]` disclosure norms.

Sharpest agent-specific risks: (1) **fabricated verification** (claiming tests pass
without running them) is the top risk and makes the whole gate theatre unless it demands
real output; (2) **over-eager `.out-of-scope/` matching** silently dismisses a different
request; (3) **unilateral close / `wontfix`** is the "a bot closed my valid issue"
backlash; (4) **disclaimer omission** under edits.

## Decision

**Adapt.** grey-matter's conventions were partly built for this skill:
`docs/agents/tkt-conventions.md` already defines the `triage:` axis (the five states), the
`kind:` axis (`bug`/`enhancement`), and the PR-request-surface flag. So most repointing
was already in place.

The framing change (the user's model): **PRs are the external request surface, tkt is the
internal unit of work, and triage is the adapter between them.** When an external
issue/PR is worth acting on, triage **mints a tkt ticket that references it** and pulls
its details in; that ticket is the unit of work, categorised/verified/groomed and closed
via `tkt close`. The external item is never the thing we close work against. Its **final
disposition** (respond / ask for more / accept+merge / decline+close) is a **user-guided**
action at the end, executed with `gh` on the maintainer's say-so. This resolves the
"two competing request surfaces" tension: there's one source of truth (tkt), and the PR
is an external artifact a ticket points at.

Built against **current tool state** per the standing rule: the live, runnable paths are
(a) grooming existing tkt tickets through `triage:` states and (b) reading a GitHub
issue/PR with `gh` today, minting a referencing ticket, and posting the user-guided final
action with `gh`. No dependence on the unbuilt `tkt import --github` (tkt 86) or native
label namespaces (tkt 193/198); the full tracker-abstraction is ticket 10 and does not
block this.

Three agent-seam adaptations (the value):

1. **Evidence-backed verification.** Step 3 must quote *real* command output / exit codes
   (the repro command, the PR test run). An unverified claim cannot become
   `ready-for-agent`; absence of real output is a `needs-info` signal. Kills the
   fabricated-verification risk.
2. **`.out-of-scope/` matching is surface-and-confirm.** The agent states the behavioral
   delta between the new request and the stored rejection and lets the maintainer decide;
   it never auto-applies `wontfix`. (Same discipline as the dedupe-before-file rule in
   retro/code-review.)
3. **Recommend-then-confirm for terminal/social actions**, and the **disclaimer is a
   template invariant** baked into every comment template, not a standalone "always start
   with" line that edits can drop.

One AGENT-BRIEF.md softening: upstream bans file paths outright, which taxes the
implementing agent with full rediscovery. Adopted the grounded middle: **stable anchors**
(module/package names, public API symbols) plus **non-binding, stale-marked** path hints,
with the rule that no instruction may *depend* on a path being current. Also tied ACs to
the ticket's `validation_criteria` so `tkt close --check-all` gates on them.

Kept: both reference files, the five states + two categories, the redundancy search, the
dedup-for-rejection vs dedup-for-existing split (a genuinely sharp insight: never log an
already-implemented wontfix into the rejection KB), the needs-info template, resume
behavior, quick-override path. Depth held at the upstream altitude.

## Cross-skill dependencies

Calls `grilling` + `domain-modeling` (or `game-modeling` for game systems) to flesh out
underspecified requests. Produces agent briefs that `implement` / `implement-spec`
consume. Uses the `triage:` and `kind:` tag axes and the PR flag from
`docs/agents/tkt-conventions.md`. `init-project` provides the tracker binding.

## Web-app bias

Minimal. The machine is domain-neutral. The only lens touch is the grilling step routing
to `game-modeling` instead of `domain-modeling` when the subject is a game system, per
the app/game split. No always-on lens pointer.
