# Proposal 12: managed guidance blocks and a stale/conflict check for agent instructions

**Status:** proposed 2026-10-27. **Scope:** `scripts/install-agents-md.mjs`, a new read-only
`scripts/check-guidance.mjs`, and the agent-guidance class of `conformance-audit`, `sync` and
`adopt-project`.

Two gaps showed up in the 2026-10-27 randomserver cutover.

1. **Whole-file ownership.** `install-agents-md.mjs` owns a target only if the file starts with
   `OWNER_MARK`. Any other file is "foreign": refused, or wiped with `--force`. The cutover hit
   this twice (`~/.codex/AGENTS.md` and `~/.config/opencode/AGENTS.md` were crew-generated), and
   `--force` threw away the whole file. A user's own rules in the same file would go too.
2. **Nothing reads guidance for rot.** Stale and conflicting lines were found by hand: `recall`
   named in 4 repo `AGENTS.md` files after the binary was removed, a recall allow rule in an agent
   config, crew's 22 KB generated steering still loaded by codex and opencode, and a symlink to a
   deleted steering file. `conformance-audit` checks *shape* (pointer-style, no duplication) but
   does not resolve what the guidance points at.

## Part 1: managed blocks, never whole files

Grey-matter content lives between markers inside any instruction file:

```
<!-- grey-matter:begin global rev=3f9a1c2 -->
...rendered source...
<!-- grey-matter:end global -->
```

- `rev` is a short hash of the block body as installed.
- **install** replaces only the block. No block and no file: create the file with just the block.
  No block in an existing file: **append** the block (dry-run prints the diff). Text outside the
  markers is never read for rewriting or removed.
- **drift:** if the installed body no longer matches `rev`, someone edited inside the block. Refuse
  and show the diff; `--force` overwrites the block only. Edits belong in the source.
- **uninstall** removes the block and, if the file is then empty, the file. A whole-file install
  made with the old `OWNER_MARK` still counts as owned and migrates to a block on next install.
- **budget:** the 3 KB limit applies to the block, not the file.
- **repo level:** `adopt-project` and `init-project` use the same primitive to add a short
  grey-matter pointer block to a repo `AGENTS.md`, instead of today's "append a line".
- Foreign generated files (a header such as "Auto-generated by ... do not edit") are not appended
  to: the check below reports them and the owner decides, since appending to a generator's output
  would be overwritten by that generator.

## Part 2: `check-guidance.mjs` (read-only)

Inputs: the four global targets, `~/.kiro/steering/*`, and a repo's `AGENTS.md`, `CLAUDE.md` and
`.kiro/steering`. Output follows `deploy.mjs audit` (findings plus exit code), and `--json`.

**Deterministic tier** (safe to report as errors):

| Check | Rule |
| --- | --- |
| dead path | a backticked or linked path that does not resolve (repo-relative, `~`, or relative to the file) |
| dead command | a backticked command at line start or in a `just`/`mise` line that is not on PATH, not a repo script, and not a recipe in the repo's `justfile` or `mise.toml` |
| dead skill | `/name` or "the `name` skill" that no installed root provides (reuses `deploy.mjs audit`'s root list) |
| dead link target | a symlink in a steering dir whose target is missing |
| foreign generator | a header matching `Auto-generated by` or `do not edit` from a tool that is not grey-matter |
| budget | block over 3 KB, or a file over a configurable limit |
| duplicate across layers | an identical normalized line in a global file and the repo file |

**Judgment tier** (surfaced, never auto-applied, consistent with `conformance-audit`):

- **Contradiction candidates.** A small committed table, `global/conflict-pairs.json`, lists
  opposed phrasings (for example "commit without asking" against "confirm before committing", or
  "use `tk`" against "never use `tk`"). A repo line that matches the opposite side of a global rule
  is reported with both file:line locations. This is a lookup, not NLP. It finds known pairs and
  nothing else, and says so in its output.
- **Intentional override.** A repo may contradict a global rule by writing
  `<!-- overrides: <rule-id> -->` above its line. Global rules get stable ids (`done-evidenced`,
  `minimal-code`). An unmarked contradiction is a finding; a marked one is listed as information.
- **Stale by age.** A rule block whose neighbouring facts changed (a file it names, a tool version
  pin) after the file's last edit is flagged "re-read", using `git log` where the repo has history.

Not attempted: judging whether prose is still true. That stays with the authors and `readme`.

## Where it runs

| Surface | What it does |
| --- | --- |
| `check-repo.mjs` | fixture tests for the installer and checker; checks `global/` source and the pair table |
| `sync` (per machine) | runs the checker on the global files and steering, after `deploy.mjs audit` |
| `conformance-audit` (per repo) | the agent-guidance class calls the checker; deterministic findings join the safe tier, judgment findings the needs-judgment tier |
| `adopt-project` | writes its pointer as a managed block; runs the checker before and after |

2. `check-guidance.mjs` deterministic tier, with fixtures taken from this cutover (dead command
   `recall`, dead steering symlink, crew generator header).
3. Judgment tier: rule ids in `global/AGENTS.md`, `conflict-pairs.json`, override markers.
4. Wire into `sync`, `conformance-audit` and `adopt-project`; update `docs/agents/harnesses.md`.

## Open questions

- Marker syntax: HTML comments render invisibly in Markdown but some harnesses may show them to the
  model as text. This is harmless to behavior, and it is also what lets the block be found again.
- Whether kiro steering files (loaded as separate files, not one `AGENTS.md`) should keep
  whole-file ownership. They are separate files, so likely yes, and blocks are for files shared with
  users or generators.
- Whether the dead-command check should consult `which` on the machine running the check or on the
  machine the guidance targets. A repo checked on one host can name a tool that exists on another.
