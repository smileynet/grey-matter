# Triage

Move work through a small state machine of triage roles. There are two surfaces, and the key idea is the **adapter** between them:

- **The external request surface** is where the outside world submits work: GitHub issues and pull requests. grey-matter does not treat its internal tracker as a public inbound queue.
- **The internal unit of work** is a **tkt ticket**. Everything we actually act on is a ticket.

**Triage is the adapter.** When an external request is worth acting on, triage **mints a tkt ticket that references it** (the issue/PR URL plus the details pulled in), and that ticket becomes the internal unit of work: categorised, verified, groomed, and closed via `tkt close` like any other. The external item is never the thing we close work against; a ticket points at it.

A **PR is a request with attached code**: same roles, same machine, with the deltas marked "for a PR" below. Its **final disposition** (respond, ask for more, accept and merge, decline and close) is a **user-guided** action at the end, not something the agent does on its own.

Every comment the agent posts to the external surface during triage **must** begin with this disclaimer, as a fixed part of the comment template, never an afterthought:

```
> *This was generated by AI during triage.*
```

## Roles

Two **category** roles (the tkt `kind:` tag): `bug` (something is broken), `enhancement` (new feature or improvement).

Five **state** roles (the tkt `triage:` tag):

- `needs-triage`: maintainer needs to evaluate
- `needs-info`: waiting on the reporter for more information
- `ready-for-agent`: fully specified, ready for an AFK agent
- `ready-for-human`: needs human implementation
- `wontfix`: will not be actioned

For a PR, the states read against the referencing ticket and its attached diff: `ready-for-agent` means a brief is attached and an agent should take the next step on the diff; `ready-for-human` means a human should take it (typically the merge).

Every triaged ticket carries exactly one `kind:` and one `triage:` tag. If two state signals conflict, flag it and ask the maintainer before doing anything else. The canonical role names and their tkt tag strings live in `docs/agents/tkt-conventions.md` (the `kind:` and `triage:` axes); if that mapping isn't present, tell the user to run `/init-project`.

State transitions: a fresh ticket goes to `triage:needs-triage` first; from there to `needs-info`, `ready-for-agent`, `ready-for-human`, or `wontfix`. `needs-info` returns to `needs-triage` once the reporter replies. The maintainer can override at any time; flag transitions that look unusual and ask before proceeding.

## Current scope

This repo uses **tkt** as its internal tracker and **GitHub** (via `gh`) as its external surface. That is the only binding this skill assumes today; a repo on a different external surface rebinds through the issue-tracker doc (the tracker-abstraction work is tracked separately and does not block this skill). Two live jobs run on current tooling:

1. **Groom internal tickets**: move existing tkt tickets through the `triage:` states.
2. **Adapt an external request**: read a GitHub issue/PR with `gh`, mint a referencing tkt ticket, run the flow against that ticket, and end with a user-guided action on the external item.

## Invocation

The maintainer invokes `/triage` and describes what they want in natural language. Interpret and act. Examples:

- "Show me anything that needs my attention"
- "Let's look at tkt 42" or "let's look at PR #17"
- "Move tkt 42 to ready-for-agent"
- "What's ready for agents to pick up?"

## Show what needs attention

Present buckets, oldest first:

1. **Untagged tkt tickets** and **`triage:needs-triage`** tickets: `tkt query` for tickets missing a `triage:` tag or carrying `needs-triage`.
2. **`triage:needs-info` with reporter activity** since the last triage notes: needs re-evaluation.
3. **External, if asked**: open GitHub issues/PRs not yet referenced by a ticket (`gh issue list`, `gh pr list`), tagged `[issue]`/`[PR]` in the display. Surface only *external*-authored PRs for discovery (a collaborator's in-flight PR is not triage work); an explicitly named PR is always triaged regardless of author.

Show a count and one-line summary per item, and let the maintainer pick.

## Triage a specific item

Whether the maintainer names a tkt ticket or an external issue/PR, the flow is the same once a ticket exists. For an external item, step 0 mints the ticket first.

0. **(External only) Mint the referencing ticket.** Read the full issue/PR with `gh` (`gh issue view <n> --comments`, or for a PR `gh pr view <n> --comments` and `gh pr diff <n>`). Create a tkt ticket that **references** it: `tkt new <slug> --title "..."`, with the issue/PR URL and a pulled-in summary (request, author, and for a PR what the diff does) in the body. This ticket is now the unit of work; the external item is linked, not duplicated-as-truth.

1. **Gather context.** Read the ticket and any prior triage notes so you don't re-ask resolved questions. Explore the codebase using the domain glossary (`GLOSSARY.md`) and respect ADRs in the area. Run two checks:
   - **Redundancy**: search for an existing implementation of the requested behavior *by domain concept*, not just the request's wording, and report where you looked. If found, it's an already-implemented `wontfix` (step 5).
   - **Prior rejection**: read `.out-of-scope/*.md` and surface any that *resembles* this request. Do not auto-apply it (see step 5).

2. **Recommend.** Tell the maintainer your `kind:` and `triage:` recommendation with reasoning, plus a brief codebase summary relevant to the request (including whether it's already implemented). Wait for direction.

3. **Verify the claim, with real evidence.** Before any grilling, check that the claim holds up, and **back it with actual command output, not prose**:
   - For a **bug**: reproduce it from the reporter's steps. Quote the real command and its output/exit code.
   - For a **PR**: check out the branch and run the relevant tests or commands. Quote the real result.
   - Report the outcome: *confirmed* (with the command output and the code path), *failed* (with the output), or *insufficient detail*. **An unverified claim cannot become `ready-for-agent`**; absence of real evidence is a `needs-info` signal, never a pass. A claim you say you verified without captured output is not verified.

4. **Grill (if needed).** If the request needs fleshing out, call the Skill tool twice, for "grilling" and "domain-modeling" (or "game-modeling" when the subject is a game system, per the app/game split in `docs/agents/tkt-conventions.md`). Grill per the grilling skill's rhythm (one question at a time by default), sharpening domain terms and updating `GLOSSARY.md`/ADRs inline as decisions land. Capture resolved points in the ticket so the work isn't lost.

5. **Apply the outcome** (tag the ticket; the agent *recommends* terminal/negative states and the maintainer confirms before any close or external action):
   - `ready-for-agent`: write an agent brief into the ticket ([AGENT-BRIEF.md](AGENT-BRIEF.md)) and tag `triage:ready-for-agent`.
   - `ready-for-human`: same brief structure, noting why it can't be delegated (judgement calls, external access, design decisions, manual testing). Tag `triage:ready-for-human`.
   - `needs-info`: post triage notes (template below) to the ticket, and to the external item if there is one. Tag `triage:needs-info`.
   - `wontfix`: tag `triage:wontfix` and close the ticket (`tkt close <id> --resolution "..."`). The comment depends on *why*:
     - **Already implemented**: point to where it lives; do **not** write to `.out-of-scope/` (that KB is for *rejected* requests, not built ones, or it poisons the dedup check).
     - **Rejected (bug)**: polite explanation, then close.
     - **Rejected (enhancement)**: write to `.out-of-scope/`, link to it from the comment, then close ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
   - `needs-triage`: apply the tag; optional comment if there's partial progress.

6. **(External only) Final action on the request, user-guided.** The tkt ticket's own done-state is `tkt close`. The external item's disposition is a **separate action the maintainer directs**: respond, ask for more info, accept and merge, or decline and close. Recommend the action, wait for the maintainer's call, then execute it with `gh` (`gh issue comment`, `gh pr comment`, `gh pr merge`, `gh issue close`), every posted comment carrying the disclaimer. Never merge, close, or decline an external request on your own authority.

## `.out-of-scope/` matching is surface-and-confirm

When step 1 finds a resembling `.out-of-scope/` entry, **do not** apply `wontfix` yourself. Semantic similarity is where an agent over-generalises and silently dismisses a legitimately different request. Instead: state the behavioral **delta** between the new request and the stored rejection ("the prior rejection was about X; this asks for Y, which differs in Z"), surface it to the maintainer, and let them confirm, reconsider, or distinguish. Only on an explicit confirm does the request join the existing file's prior-requests list and close.

## Quick state override

If the maintainer says "move tkt 42 to ready-for-agent", trust them: confirm what you're about to do (tag changes, comment, close) and act. Skip grilling. If moving to `ready-for-agent` with no grilling session, ask whether they want an agent brief first.

## Needs-info template

```markdown
> *This was generated by AI during triage.*

## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Capture everything resolved during grilling under "established so far" so the work isn't lost. Questions must be specific and actionable, not "please provide more info".

## Resuming a previous session

If prior triage notes exist on the ticket or external item, read them, check whether the reporter has answered any outstanding questions, and present an updated picture before continuing. Don't re-ask resolved questions.
